# 0.6.0 Release Verification

Full pre-release sweep: every MCP tool that does not need an API key, exercised
on all three supported runtimes, plus a verdict on every issue this fork has
open or has previously closed with unfinished items.

- **Date:** 2026-08-28
- **Branch:** `feat/isaac-sim-6.0.0-support`
- **Baseline commit:** `ebf403c`
- **Host:** Ubuntu, Linux 6.8.0-138-generic, RTX 3090 (24 GB), driver 580.173.02
- **Runtimes:** Isaac Sim 5.1.0 (V5 adapter), 6.0.1 PhysX (V6), 6.0.1 Newton (V6)

## Method

Driven live through the MCP connector (`mcp__isaac-sim__*`), so the whole chain
is under test — FastMCP tool layer, socket hop, handler registry, adapter — not
just the extension's socket surface. `scripts/smoke_test.py` covers 11 tools
over the raw socket; this sweep covers 37 over the real client path.

**Every check is a read-back assertion, never a status check.** The headline
0.6.0 bug was "eight tools reported success for input that did nothing", so a
sweep that trusts `status: success` would reproduce exactly the blindness the
release was meant to fix. `transform_object` is followed by `get_prim_info`;
`set_joint_positions` by `get_joint_positions` with `position_source` inspected;
`delete_object` by `list_prims`. Negative cases (typo'd prim path, wrong-length
array, `size <= 0`, negative step count) assert the tool *errors* rather than
lying.

**One Isaac Sim instance at a time.** A second concurrent instance exhausts VRAM
on a single GPU and causes device-lost crashes. Each runtime is cold-booted,
swept, and killed before the next boots.

**Measure all three, then fix.** No code changes land mid-campaign: a fix to
shared code (`adapters/base.py`, `handlers/`) would invalidate every runtime
already swept. Failures are recorded and triaged in one pass at the end.

Results are appended **as each phase completes**, so a Kit crash costs one phase
rather than a whole sweep.

## Phase order

Ordered so state accumulates instead of being rebuilt, and so the two known
ordering hazards are respected: sensors run late because issue #20 strands the
*first* RTX camera of a Kit session, and graphs run last because they need
`play`, which must not be mixed with the step-only debug loop.

1. **Identity** — `get_simulation_state` (adapter, engine, version)
2. **Scene** — `get_scene_info`, `clear_scene`, `create_physics_scene`, `list_prims`, `get_prim_info`, `list_environments`, `load_environment`
3. **Objects** — `create_object` (every type), `transform_object`, `clone_object`, `delete_object`, negatives
4. **Lighting / materials** — `create_light`, `modify_light`, `create_material`, `apply_material`
5. **Robots** — `list_available_robots`, `refresh_robot_library`, `create_robot`, `get_robot_info`, `get_joint_config`, `set_joint_positions`, `get_joint_positions`, two-robot GPU check
6. **Simulation** — `set_physics_params`, `step_simulation`, `play`/`pause`/`stop`, `get_physics_state`, `get_isaac_logs`, `execute_script`, `reload_script`
7. **Sensors** — `create_camera` (+`target`), `capture_image`, camera delete, `create_lidar`, `get_lidar_point_cloud`
8. **Assets** — `load_usd`, `import_urdf`
9. **Graphs** — `create_action_graph` (`script_file` + `inline_script`), `edit_action_graph`, play, logs

**Issue #20 — CONFIRMED, reproduces as documented.** Four cameras created, all
four deleted with success; `/World/Cam0` — the session's first — survived.
`CAMS: ['/World/Cam0']`. Cameras 1-3 removed cleanly. The warning fired on the

**F11 (provisional) — two robots produced garbage joint values on 6.0 PhysX.**
Both articulations read `-431602080.0` on every DOF (the 0xCDCDCDCD
uninitialised-memory sentinel) while `step_simulation` reported
`status: success`. Kit log carried `CUDA error 700: cudaErrorIllegalAddress`
and `PhysX has reported too many errors, simulation has been stopped` — the
exact signature 0.6.0 claims to have fixed.

**RETRACTED as a two-robot regression.** Three isolation runs on a fresh boot
all passed:

1. Two robots, no sensors, step 30 → sane values on both.
2. Same, then command both and step 150 → both converge exactly
   (ArmA j2 -0.3984 / j4 -2.0005 / j6 1.49999; ArmB 0.4999 / -0.9997 / 0.8001).
3. Camera + lidar + capture + play/stop, then step → still sane.
4. Create 2 cameras + 1 lidar, delete all three, then step → still sane.

**The trigger was mine.** In the failing run my diagnostic `execute_script`
calls constructed extra `LidarSensor(path="/World/Lidar1",
annotators=["generic-model-output"])` objects on a prim that was later deleted,
and never released them — matching the log's
`PhysX error: Failed to unload CUDA module data, returned 700`. The two-robot
GPU fix **holds on 6.0.1 PhysX**.

**What survives as a real finding (F11, revised).** When PhysX had died,
`step_simulation` returned `status: success` with every joint reading
`-431602080.0` — an uninitialised-memory sentinel served as a measurement. The
project's stated contract is that a dead pipeline must not be reported as
success (`get_joint_positions` already distinguishes `position_source`). A
sentinel-value / dead-scene guard on `step_simulation` would have turned this
into an error instead of a plausible-looking number. Trigger was self-inflicted;
the missing guard is not.

### F13 — a free rigid body is never simulated on Newton

**Severity: high.** `create_object(physics_enabled=True)` produces a prim with
`RigidBodyAPI` enabled, non-kinematic, `CollisionAPI` applied — which then never
moves. Measured on a minimal clean scene (clear → physics scene → one cube at
z=3, gravity -9.81):

- `step_simulation` 60, 40, and 200 frames → position stays `(0, 0, 3)`,
  `linear_velocity` `(0,0,0)`, `"stepping": "exact"` each time.
- `play_simulation` free-run for 4 s → still zero velocity via
  `get_physics_state`.
- Not a read-source artefact: **Fabric itself** reports `_worldPosition =
  (-2, 0, 3)`, i.e. the body genuinely has not moved.
- The same scene on 6.0 PhysX gives -3.107 m/s after 20 steps.

Articulations *do* simulate on Newton (the FR3 moves — it just diverges, per
#21), so the gap is specific to free rigid bodies. Root cause may lie in
Newton's USD→MuJoCo model building rather than in this repo, but it is
user-visible on a supported engine and the "Newton engine parity" claim covers
it.

### F10 — `get_lidar_point_cloud` returns spherical data labelled as Cartesian (6.0)

**Severity: high — silent wrong answer.** On 6.0 the tool returns
`(azimuth°, elevation°, range m)` while reporting
`"frame": "sensor-local coordinates, meters"`, Cartesian `bounds`, and a
`nearest.point`. Anyone deriving obstacle positions from it gets nonsense.

Measured with a 2 m cube directly ahead of a lidar at `(0,0,1)`:

| Wall position | col 1 range | col 3 | True geometry |
|---|---|---|---|
| x = 4 (face at 3 m) | ±18.41 | 2.996 – 3.276 | `atan(1/3)` = **18.43°**, range **3 m** |
| x = 10 (face at 9 m) | ±6.31 | 8.991 – 9.114 | `atan(1/9)` = **6.34°**, range **9 m** |

Column 2 values (-6.13, -1.29, 3.55) are literal entries of the sensor's
`emitterState:s001:elevationDeg`; the first read spanned exactly its full
[-15.0, 10.0].

**Root cause.** The lidar prim carries
`omni:sensor:Core:elementsCoordsType = SPHERICAL`, so `GenericModelOutput`'s
`x/y/z` are azimuth/elevation/range. `v6.py:get_lidar_point_cloud` stacks them
unconverted, and `handlers/sensors.py` then computes `nearest.distance` as
`sqrt(az² + el² + range²)` and stamps the Cartesian frame label. This is the
same family as the already-fixed "returned the raw byte buffer" bug: the port
adopted 6.0's unified annotator without adopting its coordinate convention.

**Not present on 5.1**, which uses the older point-cloud annotator: a lidar 1 m
above ground returned z ∈ [-0.98, -0.11] — correctly Cartesian.

### Retractions

Three findings were withdrawn after isolation. All three were caused by the test
process, not the product — which is the main reason this campaign measured all
three runtimes before changing any code:

- **F1 / F2** — a `RuntimeError` storm and a stray root `PhysicsScene` came from
  `uv run pytest`, whose `tests/test_integration.py` drives the live socket on
  :8766 and fired at Kit while it was still booting.
- **F11 as a two-robot regression** — garbage joint values and CUDA 700 came
  from my own diagnostic `execute_script` leaking `LidarSensor` annotators onto
  a prim that was later deleted. Four clean-boot isolation runs all passed.

**Process note for the next sweep: never run the unit suite while a runtime
under test is up, and never construct sensor wrappers from `execute_script`
against prims you intend to delete.**
